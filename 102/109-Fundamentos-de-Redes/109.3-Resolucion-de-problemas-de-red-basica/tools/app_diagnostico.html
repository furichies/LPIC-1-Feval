109.3 Resolución de problemas de red básica

Objetivo 109.3 · Lección: flujo ip → ss → ping → traceroute → netcat · Peso v5.0: 4

ip · ss · ping · traceroute · nc · iproute2

1 · Flujo de diagnóstico (pulsa cada paso)

  1. 1. ¿Tengo IP? ip -brief addr — sin IP no hay nada que depurar.
  2. 2. ¿Ruta por defecto? ip route — busca la línea default via ….
  3. 3. ¿Escucha el servicio? ss -tlnp — comprueba puerto y proceso.
  4. 4. ¿Llego al destino? ping -c3 8.8.8.8 y traceroute ejemplo.es.
  5. 5. ¿Responde el puerto? nc -vz destino puerto — prueba TCP rápida.

2 · net-tools (legacy) vs iproute2 (actual)

En el examen cae: lo viejo está obsoleto, usa ip y ss.

Memoria rápida: si ves ifconfig, route o netstat en una opción de test, sospecha: suelen ser la respuesta incorrecta salvo que pregunten por legacy.

Excepción: arp -a aún aparece en sistemas viejos, pero en Linux actual toca ip neigh.

3 · Interpreta salidas reales

Despliega cada caso, lee la salida y deduce el fallo como en el examen.

Caso A · ¿Hay IP? — ip -brief addr

lo UP 127.0.0.1/8

enp0s3 DOWN (sin IP)

Diagnóstico: la interfaz está caída, no es fallo de DNS ni de ruta.

Acción: nmcli dev status y nmcli con up "casa".

Revisa cable o Wi-Fi antes de mirar nada más.

Caso B · ¿Hay ruta? — ip route

192.168.1.0/24 dev enp0s3 scope link

(no hay línea default)

Diagnóstico: hay red local pero falta puerta de enlace.

Llegas al vecino, no a internet.

Acción: fijar gateway en nmcli o ip route add default via 192.168.1.1.

Caso C · ¿Escucha? — ss -tlnp

LISTEN 0.0.0.0:22 (sshd)

(nada en el puerto 80)

Diagnóstico: SSH funciona, pero no hay servidor web escuchando.

Si esperabas una web, el demonio está parado o mal configurado.

Acción: systemctl status apache2 (o nginx) y firewall.

Caso D · ¿DNS o red? — ping doble

ping -c2 8.8.8.8 → 0% pérdida

ping -c2 ejemplo.es → fallo temporal de resolución

Diagnóstico: la red va, lo roto es la resolución de nombres.

Acción: cat /etc/resolv.conf y grep hosts /etc/nsswitch.conf.

Regla de oro: IP responde + nombre no = culpa del DNS.

Caso E · ¿Puerto abierto? — nc -vz

nc -vz 192.168.1.10 22 → succeeded

nc -vz 192.168.1.10 80 → connection refused

Diagnóstico: el equipo está vivo; el puerto 80 cerrado o filtrado.

Acción: servicio, ss -tlnp en el servidor y reglas del cortafuegos.
